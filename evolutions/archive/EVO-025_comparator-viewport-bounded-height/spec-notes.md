# Spec Notes — EVO-025

## PRD interpretations

- **"Navbar height" = live rendered height of the `<header>` produced by `Navbar.jsx`.** The PRD references the "Navbar surface" (sticky header at the top of the page) without specifying whether the value is the design-time token or the live measurement. The existing token `--navbar-height: 5rem;` (80 px) does not match the actual rendered height (~65 px = `h-16` + 1 px border). The cap formula in FR-001 subtracts the actual height, so the variable is rewritten at runtime from the Navbar component. This is captured in AD-002.
- **"12 px margin" is interpreted as a literal 12 px in the cap formula**, not a design token. The PRD lists it as a numeric constant inside the formula and not as a styling rule between elements. It is therefore embedded in the `calc(...)` expression as `12px` and not introduced as a new spacing token.
- **Desktop breakpoint = Tailwind `lg` (1024 px)**, because that is the breakpoint at which `MiniComparator.jsx` already switches from stacked to side-by-side (`lg:grid-cols-[320px_1fr]` at line 39). The PRD explicitly states "no new breakpoint is introduced".
- **FR-002 ("no forced minimum, no padding to fill the cap")** is implemented by combining the existing `h-fit` on `FilterPanel` with `max-h-[...]`. Using `max-h` (and **not** `h-`) is what guarantees natural content height below the cap. For `ComparisonTable`, the card root is `lg:flex lg:flex-col lg:max-h-[...]` — flex children only fill the cap if they have `flex-grow > 0`; the inner scroll wrapper uses default `flex-grow: 0` plus `min-h-0`, which means it sizes to its content and the card shrinks to the inner content height when below the cap.
- **The cap applies to the panel root, not to the inner scroll region**, so the card header (`<h3>` + count of wheels) is also bounded by the cap and remains visible above the scrolling rows. This matches the spirit of the PRD: the user must keep both panels usable and read the count while scrolling rows.
- **Mobile drawer is out of scope.** The mobile drawer container in `MiniComparator.jsx` already has `overflow-y-auto` and `inset-y-0`; that pre-existing behavior is preserved untouched. The PRD's FR-007 only says the cap doesn't apply below the breakpoint; nothing in this evolution alters the mobile drawer.

## Architecture decision rationale

### AD-001 — CSS `calc` over a JS hook
The PRD's FR-006 demands reactive recompute on viewport change. The cheapest implementation is a CSS expression: `vh` already reacts to viewport-height changes, so a `calc(100vh - var(--navbar-height) - 12px)` expression is reactive by construction with no JS. A JS hook would add state churn and a `window.resize` listener for no functional benefit. The cost of using a CSS expression is that JSDOM does not evaluate `vh`, so AC-001 / AC-002 are validated against the **resolved CSS string** rather than the computed pixel value — this is acknowledged in TASK-004.

### AD-002 — Runtime measurement of `--navbar-height`
The static design-token value (5 rem / 80 px) mismatches the live Navbar height (~65 px). Subtracting the wrong value from `100vh` would systematically over-cap the panels (the cap would be 15 px smaller than the spec) and create a visible gap at the bottom of the Navbar. Measuring at runtime fixes this once and for all consumers of `--navbar-height` (currently also `index.css`'s `scroll-padding-top` and `FilterPanel.jsx`'s former `top: var(--navbar-height)`).

### AD-003 — Drop `lg:sticky` on `FilterPanel`
With the cap and an internal scroll region, `position: sticky` becomes redundant and conflicts: the panel is already bounded at the top of the available viewport by the grid layout + `max-h`, and any sticky behavior would create a second scroll behavior on top of the internal scroll. Keeping `lg:sticky` would also leak a `top: var(--navbar-height)` reference that no longer matches the new vertical model (cap from the **panel top**, not from the Navbar bottom — the 12 px margin in the cap formula plays that role).

### AD-004 — Flex column + `min-h-0` on the scroll child
This is the canonical CSS pattern. The non-obvious detail is `min-h-0`: without it, the flex child refuses to shrink below its intrinsic content height and the cap is silently ignored. This is documented inside TASK-003 so the implementer does not omit it.

### AD-005 — Keep `overflow-hidden` on the card root
`overflow-hidden` on the card root is preserved because it clips the rounded card corners over the inner scroll region. It does not prevent the `sticky` `<thead>` from working because the sticky scope is the inner `<div className="overflow-x-auto lg:overflow-y-auto">`, not the card root. (Sticky elements stick relative to the nearest scrolling ancestor with `overflow` that creates a scroll context — which is the inner wrapper.) This is the reverse of the worry recorded as a risk in `tech-specs.md` and was verified by re-reading the structure during spec writing; the risk entry is kept for the implementer's attention.

### AD-006 — Inline `useLayoutEffect` over a shared hook
One consumer today; abstracting prematurely would add a file with no second user. If a second sticky surface ever needs the same treatment, the extraction is a 5-minute refactor.

## Tradeoffs

- **CSS cap vs JS hook.** Chose CSS for zero render cost and zero new state. Tradeoff: JSDOM can't compute the resulting pixel value, so some ACs are validated against the resolved CSS string in TASK-004 — a contract-level rather than layout-level assertion. Considered acceptable because the contract *is* what the implementation owns; layout correctness is verified by the manual ACs (AC-008) and by the visible browser-level smoke check.
- **`100vh` vs `100dvh`.** `100dvh` is generally preferred per `ui-guidelines.md` to avoid mobile Safari address-bar jumps. Here the cap applies only at `lg` (≥ 1024 px) where there is no mobile-browser chrome jump, so `100vh` is correct and matches the PRD wording literally. Using `100dvh` would also work but would be an undocumented deviation from the PRD formula.
- **Sticky `<thead>` via CSS `position: sticky` vs a fixed sticky header outside the table.** Chose CSS sticky on `<thead>` because it requires no DOM restructuring of the existing semantic `<table>`. The alternative (a duplicated, absolutely-positioned `<div>` header above the scroll region) would have introduced a column-width-syncing problem identical to the one already solved for `WheelDetailPanel` via `ResizeObserver` — unnecessary complexity for this evolution.
- **Adding `@testing-library/react` for TASK-004 vs sticking with `renderToStaticMarkup`.** The integration assertions in TASK-004 (`scrollTop`, `getComputedStyle`, scroll-isolation) require a JSDOM-mounted render, not a static string. `renderToStaticMarkup` would only allow className substring checks (which TASK-002 / TASK-003 unit tests already cover). The proposed direction is to add `@testing-library/react` and `@testing-library/jest-dom` as `devDependencies` — small, well-maintained, and unlocks every future DOM-level test the project might want. The decision is left to the implementer of TASK-004 and recorded under "Open questions" below for explicit confirmation before merge.

## Deviations from project conventions

- **Mutating `:root` style from a component.** `Navbar.jsx` will write a property on `document.documentElement` (CSS variable). This is the first place in the codebase to do so. It is justified by the fact that the variable is consumed by global CSS (`index.css`'s `scroll-padding-top`) and by Tailwind arbitrary-value classes, both of which read from the root scope. Encapsulating the write inside the Navbar component keeps the producer/consumer relationship clear and removes the risk of stale values. No other component should adopt this pattern without a similar justification — recorded here so a future reviewer does not generalize it.

## Implementation notes — TASK-004

- **OQ-001 resolved — kept option (b).** TASK-004's integration suite uses `createRoot` + React 19's `act` (the same pattern as `Navbar.test.jsx`), without adding `@testing-library/react` / `@testing-library/jest-dom` as `devDependencies`. Rationale: the seven required assertions only need DOM-mounted access (`getComputedStyle`, `scrollTop`, `scrollHeight`, `clientHeight`, `querySelector`) — none of them benefit from `@testing-library`'s user-event simulation, async queries, or accessibility-tree traversal. Adopting `@testing-library/react` later (option (a)) remains a 1-line `package.json` change.
- **JSDOM does not evaluate `@media` queries.** A quick probe confirmed that CSS rules nested inside `@media (min-width: 1024px) { ... }` are reported as `'none'` by `getComputedStyle`, regardless of `window.innerWidth`. This contradicts the optimistic note in TASK-004's "Required context" ("JSDOM honours the lg: media-queried rule"). To preserve a faithful CSS-contract check, the test injects two stylesheets: a base sheet (always mounted, holds the non-responsive `.sticky` / `.top-0` rules) and an `lg` sheet that is appended / removed by the `setDesktopMatchMedia()` / `setMobileMatchMedia()` helpers. The injection mirrors what Tailwind compiles in production for the exact class names present on the rendered DOM.
- **AC-005 downgrade.** JSDOM defaults `scrollHeight` and `clientHeight` to `0` on every element (no layout). The "no internal scrollbar" assertion is therefore validated by stubbing both properties to the same value (`400 px`) on each root via `Object.defineProperty`, then asserting `scrollHeight === clientHeight`. This is a contract-level downgrade vs. a layout-level measurement: the test confirms the **structural promise** ("when content fits, no overflow") rather than computing real layout. Recorded here per the TASK-004 "Tradeoffs" requirement.
- **`react-i18next` mock not introduced.** TASK-004 mentions a "minimal `react-i18next` mock that returns the translation key unchanged, matching the pattern used by `Hero.test.jsx` and `Footer.test.jsx`". Inspection of those files shows that they do **not** mock `react-i18next` — they rely on the library's built-in behavior when no instance is initialized (`useTranslation` returns the key as the translation, while logging an info-level warning). The new test follows the same pattern: no mock is added, the warning is benign and identical to the one already emitted by `Navbar.test.jsx`.
- **`matchMedia` shim added to `test-setup.js`.** JSDOM does not implement `window.matchMedia`; tests set `globalThis.__matchMediaMatches` to a predicate and the shim returns the matching result. This keeps the shim small enough for test-only use, and only the new viewport-cap suite reads from it. The shim is gated by a `typeof` check so it does not break the existing `node` environment used by other suites.

## Implementation notes — TASK-001

- **JSDOM environment for `Navbar.test.jsx`.** The existing test suite ran under Vitest's default `node` environment with `renderToStaticMarkup`. TASK-001's "Tests to implement" section requires asserting on `document.documentElement.style.getPropertyValue('--navbar-height')` after a mount/unmount cycle, which needs a real DOM. The chosen path was:
  - Add `jsdom` as a `devDependency` (test-tooling only; no runtime impact and no new dependency on the component code itself).
  - Switch only `Navbar.test.jsx` to JSDOM via the `// @vitest-environment jsdom` docblock so the rest of the suite keeps the lighter `node` environment.
  - Use `react-dom/client`'s `createRoot` + React 19's exported `act` to mount/unmount the component; no testing-library dependency is introduced.
  - Stub `HTMLElement.prototype.offsetHeight` (via `Object.defineProperty`) inside the test rather than via the layout engine, since JSDOM has no real layout.
  - Install a minimal `ResizeObserver` shim in `src/test-setup.js`. The shim records every instance under `ResizeObserver.instances` and exposes a `trigger()` helper, so the resize-update test can synchronously fire the observer callback after the stubbed `offsetHeight` is changed.
- **`IS_REACT_ACT_ENVIRONMENT` flag.** Set in `test-setup.js` so React 19's `act(...)` does not emit the "not configured to support act(...)" warning during mounting and unmounting.
- **Pre-existing failing tests.** `Hero.test.jsx` ("renders the stat metrics grid exactly once") and `Footer.test.jsx` ("renders copyright notice") fail on the unchanged baseline (they assert on resolved i18n strings while `useTranslation` returns the raw keys in the test environment). They are unrelated to TASK-001, were not touched, and remain failing.

## Open questions

- **OQ-001 — `@testing-library/react` adoption.** TASK-004 needs a JSDOM-mounted render. Two options:
  (a) Add `@testing-library/react` + `@testing-library/jest-dom` as `devDependencies` (~2 small packages, MIT, react 19 compatible).
  (b) Use `react-dom/client`'s `createRoot` + manual `act()` + raw `document.querySelector`.
  Recommendation: (a). Awaiting confirmation before TASK-004 is started.

- **OQ-002 — Test approach for Redux Provider in TASK-002 / TASK-003 unit tests.** The existing test pattern (`renderToStaticMarkup`) works with Provider but yields a flat HTML string that has to be searched with substring matches for class names. Acceptable here because the unit tests only verify class presence. Confirmed: stay with `renderToStaticMarkup` for TASK-002 / TASK-003 className assertions, and switch to a real DOM mount only for TASK-004. Recorded for the implementer's reference.

- **OQ-003 — Does the `index.css` `scroll-padding-top: var(--navbar-height)` change behavior once `--navbar-height` becomes a smaller value (~65 px instead of 80 px)?** Anchor links to `#tool`, `#roadmap`, `#partnerships`, etc. will land 15 px closer to the top of the viewport (visually under the Navbar by 0 px instead of 15 px). This is a side effect of correcting the variable, not a regression of this evolution. Flagged for visual verification during AC-008 manual testing. If the previous 15 px breathing room is desired, a follow-up evolution can introduce an explicit `--scroll-anchor-offset` token; not required here.

- **OQ-004 — Cap interaction with the `MiniComparator` section's vertical padding (`section py-16 sm:py-20 lg:py-24`).** The section wrapper has top padding that pushes the panels below the Navbar by a larger amount than 12 px when the user scrolls to the top of the section. The 12 px margin in the cap is a hard cap of the **panel's max height**, not a layout margin between Navbar and panel; the section padding remains independent. No conflict — but flagged in case visual review expects the 12 px to be a visible gap between the Navbar bottom and the panel top.
