### 🟠 Important

**Tire-width filter bounds hide valid supported widths**
- 📍 `frontend/src/store/selectors/wheelsSelectors.js:184`
- 📍 `frontend/src/store/selectors/wheelsSelectors.js:191`
- 📍 `frontend/src/store/slices/filtersSlice.js:27`
- 📍 `frontend/src/config/wheelProperties.jsx:536`
- 📍 `frontend/src/config/wheelProperties.jsx:542`
- 📍 `frontend/src/data/wheelsData_mavic.js:421`
- **Problem:** `tireWidth` filters by `filterAccessor` as an interval, but both `makeSelectRangeBoundsFor` and `buildInitialFilters` compute range bounds with `property.accessor`. For `tireWidth`, that accessor returns `max ?? min`, so a wheel with `tire_width_mm: { min: 19, max: 62 }` contributes `62` to the lower-bound calculation instead of `19`. In the current catalog, the real minimum supported width is `19`, while the UI bound computed this way starts at `23`.
- **Impact:** A user cannot set the tire-width filter to values such as 19-22 mm even though the catalog contains wheels supporting those widths. The filter behavior itself supports interval overlap, but the UI prevents users from selecting the full data range.
- **Fix:** Teach range-bound initialization to use `filterAccessor` when present. For object intervals, include finite `min` and `max`; for arrays, include finite entries; for scalars, include the scalar. Use the same helper in `buildInitialFilters` and `makeSelectRangeBoundsFor`.

**ETRTO ranges are parsed after the generic range matcher**
- 📍 `scripts/codemods/other-specs-promote.mjs:1618`
- 📍 `scripts/codemods/other-specs-promote.mjs:1627`
- 📍 `evolutions/PROJ-001_other-specs-promotion/EVO-058_tire-width-mm.md:129`
- **Problem:** `parseTireWidthRange` checks the generic `25-622` style range regex before the specific ETRTO range regex. For an input the EVO explicitly names, `25-622 - 32-622`, the generic matcher grabs `25` and `622` first, returning `{ min: 25, max: 622 }` instead of `{ min: 25, max: 32 }`.
- **Impact:** Re-running the codemod, or using it as the documented migration harness for future source data, can create impossible tire-width maxima and make the tire-width filter/column misleading.
- **Fix:** Move the ETRTO range and single ETRTO checks before the generic range matcher, then add a codemod-level regression test for `25-622 - 32-622`.

### 🟡 Suggestions

**Split the codemod if it remains a maintained tool**
- 📍 `scripts/codemods/other-specs-promote.mjs:40`
- **Problem:** The migration script is 1,806 lines and contains every concept parser in one file. This weakens the project plan's "isolated per concept" intent: the concepts are selectable, but not structurally isolated.
- **Impact:** The next schema promotion or parser fix must navigate unrelated migration logic, increasing regression risk in old concepts.
- **Fix:** Keep the CLI wrapper, but move each concept into `scripts/codemods/other-specs/<concept>.mjs` with focused parser tests.
