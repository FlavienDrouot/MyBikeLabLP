# Phase 2 — acquisition

Read `00-shared-contract.md` and `catalog-index.json`. Acquire source facts for every included candidate and every unresolved candidate that can be investigated. Produce exactly one logical evidence JSON file per product family. Do not create one file per configuration, and do not create temporary small-batch evidence files as part of this contract. A family file may contain many profiles and observations.

Use the deterministic filename `product-family-evidence-<discovery-slug>.json`, where the slug is trimmed, lower-case, and made by replacing every run of characters outside `[a-z0-9]` with `-`; trim leading and trailing hyphens. Never use a path separator or append a counter. If two families produce the same filename, route the collision to `04-exceptions.md` instead of overwriting an artifact.

## Method

WebFetch/static HTTP is a preparatory read-only pass. Use it to inspect HTML, JSON-LD, embedded product data, technical links, specification tables, and stable facts. Record its provenance. It can discover selectors, URLs, labels, and candidate values; it cannot establish dynamic commerce/UI facts or replace interactive verification.

Acquire technical facts for each wheel separately whenever the source distinguishes front and rear: begin with front weight and rear weight, and preserve the displayed source label, raw value, numeric value when directly stated, unit, and applicability. Store each fact at its narrowest supported scope (`stable`, `profile`, or `observation`), using the existing fact location for that scope. Every such fact must include `side` (`front`, `rear`, or `wheelset`), `source_label`, `scope`, and one or more `provenance` entries in addition to the normal fact fields. Each provenance entry must identify the source ID, locator, retrieval time, and acquisition method; it must agree with the source registry. Capture a published wheelset/total weight when available as a separate `side: "wheelset"` fact; never replace, merge, or calculate it from per-wheel facts. Do not convert units or infer a missing side from the other side or from a total.

Capture first-party image URLs as facts, without downloading images. Inspect HTML `img`/`srcset`, OpenGraph metadata, JSON-LD, product-gallery markup, and dynamic configuration-gallery data. Preserve the exact URL, source label or attribute, locator, selected configuration context, and provenance. Deduplicate identical URLs within the family artifact while retaining every distinct supporting provenance entry. When a selector changes the gallery, re-read the settled gallery after the browser assertion and associate newly exposed URLs with that observation; do not assume the initial gallery applies to every configuration. Ignore third-party, tracking, placeholder, and non-URL values.

Acquisition workers MUST use the Codex integrated in-app browser for every buyable configuration that is in scope or whose purchase unit remains ambiguous, and for all dynamic commerce/UI facts. A configuration deterministically identified during the preparatory pass as an individual wheel may be recorded as an out-of-scope exclusion without full selector traversal. For an in-scope or ambiguous configuration, open the product page, all specification tabs, linked technical documents, and relevant first-party support pages. Interact with its selectors in the integrated browser and capture the resulting visible state, including selected values, SKU, stock, price, currency, and URL after selection when exposed. After every selector action, assert the settled state from the changed visible label or semantic control; do not target an `sr-only` input directly. Do not record an attempted configuration as settled unless that assertion passes. Do not silently replace the integrated browser with static HTTP or another fallback. If browser interaction is unavailable or fails for an in-scope or ambiguous configuration, record the attempted configuration with blocked unresolved fields and route the exception through `04-exceptions.md`; do not continue as though verification succeeded. Check retailer and manufacturer offers only when they are in scope for the source run. Capture technical rows and bounded excerpts, not whole pages.

Do not classify any axis. Record only its raw identity and observation context: source label, raw value, normalized display value when safe, control type, source fact IDs, and whether it is page-level or selection-scoped. Do not use `variant`, `option`, `cosmetic`, `offer`, or `unknown` as an acquisition classification. Do not allocate canonical IDs in this phase; evidence IDs and keys must follow the compact deterministic guidance below.

Profiles are reusable by exact raw axis/value identity within the same source scope, or by a genuinely reusable multi-axis fact supported across observations. Use one profile for a raw axis/value pair that recurs; never create one profile for each Cartesian combination. Reuse is based on the source scope and raw axis/value identity, not an LLM guess. If reuse is uncertain, keep the profiles separate. A profile must not contain a repeated `selected configuration` fact for every observation. A fact that applies only to one observed combination may be stored inline under that observation only when it is directly evidenced, not reusable by any individual axis/value or broader source scope, and not worth a full combination profile; give it an `obs-` fact ID and do not copy profile or stable facts into it.

## Operational traversal and recovery

Process no more than six configurations in one traversal checkpoint. Keep one logical family artifact; do not create temporary small-batch files or extra workers. Persist completed observations before proceeding to the next checkpoint. Each requested configuration must be accounted for as settled, excluded, or unresolved before the checkpoint is considered complete.

If any browser call times out, reinitialize the browser session and verify the last persisted observation. Resume from the first missing configuration. A timeout is not evidence of completion: never assume the call completed, and never emit a duplicate observation ID. If the prior result cannot be verified, preserve the attempted configuration as unresolved and continue with the first missing configuration.

## Exact output rules

- `stable_facts` contains only page-level/family-level facts reusable without a selection. Each fact has a `stable-` ID. Technical facts preserve separate `side` values (`front`, `rear`, or `wheelset`), the exact `source_label`, `scope` (`stable`, `profile`, or `observation`), and one or more `provenance` entries containing `source_id`, `source_locator`, `retrieved_at`, and `method`. A published wheelset weight is independent from front and rear facts.
- `configuration_profiles` contains reusable raw axis/value profiles, or genuinely reusable multi-axis profiles, and selection-scoped facts. Each profile fact has a `profile-` ID. Profiles do not imply catalog identity or classification. Profile IDs and keys must be deterministic and compact: lowercase the raw axis label and value, replace each run outside `[a-z0-9]` with `-`, trim hyphens, and use `profile-<axis>-<value>` plus `profile_key: "<axis>=<value>"`; append a stable source-scope slug only when needed to avoid a collision. Do not use observation order or Cartesian-combination order.
- `observations` is compact. Each record is one attempted or browser-verified configuration and references plural `profile_ids` for its reusable axis/value profiles. It may contain `facts` only for observation-specific or exact-combination delta facts, each with an `obs-` ID; it must not repeat stable/profile facts. Every in-scope or ambiguous buyable observation requires `method: "in_app_browser"` provenance through its `source_id`; a deterministically excluded individual wheel needs only exclusion evidence.
- After every selector action, the browser must assert the settled state using the visible label or semantic control. Do not target `sr-only` inputs directly, and do not mark an attempted configuration as settled without the assertion.
- `sources` is the provenance registry. `method: "static_http"` is preparatory and may support stable page facts only. `method: "in_app_browser"` is required for dynamic and selection-scoped facts and every in-scope or ambiguous buyable configuration.
- Image URLs are represented by facts labeled `Product image URL` (or the exact source label), with the URL as `value` and `raw_value`. Capture first-party URLs found in `img`/`srcset`, OpenGraph, JSON-LD, product galleries, and dynamic configuration galleries; deduplicate identical URLs within the family artifact and preserve all distinct provenance entries. A selector-driven gallery must be captured only after the browser asserts the settled selection. Do not download images.
- `matrix_coverage` records raw axes, labels, control types, tested raw values, observed raw values, source IDs, and whether coverage is complete. It does not classify axes or count canonical products.
- `unresolved` records every missing comparison fact and every failed or unavailable browser verification with `field`, `reason`, `source_ids`, and `severity` (`unknown|blocked|conflict|stale|low|medium`). A blocked browser pass must not be represented as a successful buyable observation.
- Missing per-wheel weight, missing published wheelset/total weight, and missing image URLs are distinct unresolved fields: use `front_weight`/`rear_weight`, `wheelset_weight`, and `image_urls` respectively, with separate reasons and provenance. Record each only when the source was checked; never fabricate, calculate, or infer any of them.
- `bounded_evidence` contains only the smallest excerpts needed to audit declared facts. Its `supports` values must be exact IDs declared in `stable_facts`, `configuration_profiles[*].facts`, or observation `facts`.
- Preserve source labels, raw values, units, wording, URLs, timestamps, and conflicts. Use `null` for unknown numeric/boolean values and `""` for unknown text only in canonical output; keep the unresolved reason here.
- Preserve source currency; never convert it. Record currency and retrieval time for every price or commerce observation. Never copy the base product URL into `url_after_selection`; if no post-selection URL is exposed, leave it empty and record a blocking unresolved item.
- Do not fabricate facts, infer unobserved configurations, copy values from sibling profiles, emit canonical wheel objects, classify axes, or allocate IDs.

Before returning the artifact, parse the JSON and validate the exact expected raw matrix cardinality after scope exclusions. Confirm that every requested configuration has exactly one settled, excluded, or unresolved disposition, with no missing or duplicate observation ID. Validate URL semantics: leave `url_after_selection` empty when the base URL is retained; otherwise record only the observed post-selection URL. Explicitly report missing price, currency, stock, SKU, and identity. Missing SKU is non-blocking only when selected raw values, buyability, and sufficient first-party identity are verified; missing identity or other required commerce fields remains unresolved with the appropriate severity. WebFetch remains preparatory, and integrated-browser verification remains mandatory for every in-scope or ambiguous configuration.

Return only valid JSON for each product family.

## Corrections

Discovery and acquisition MUST determine the purchase unit before treating an observation as in scope. The current catalog accepts only a front + rear wheelset sold together. Capture raw `axis_applicability` on every observation and profile axis. Use `applicable` for a present side and `not_applicable` for explicit front-only or rear-only sentinels, including `None (Front Wheel Only)` and `None (Rear Wheel Only)`. Mark those observations `scope_status: "excluded_single_wheel"`, preserve their source and exclusion reason, and do not create null profiles, cardinality exceptions, or canonical products for them. Only in-scope pair observations enter normalization. This is mechanical scope capture, not variant, option, cosmetic, or offer classification.

SKU is optional for an in-scope wheelset. When selected raw values and buyability are browser-verified, a post-selection URL, variant ID, or another sufficient first-party identity is enough to identify the observation without a SKU. Record the absent SKU in `unresolved` with severity `low` or `medium`; it is blocking only when SKU is the sole reliable identity. Extend the unresolved severity values to include `low` and `medium`. A missing post-selection URL is blocking only when no sufficient first-party identity is observed. Preserve browser/static provenance.
